# Database migrations — how they run, and how they break

Current as of the Corridor-One go-live push. A status document, not an
aspiration: the **Known hazards** below are live risks today, not things already
handled.

## How migrations reach production

`packages/db/migrations/*.sql` are generated by `drizzle-kit generate` and applied
by `bun run db:migrate` (`packages/db/src/migrate.ts`). Drizzle records each
applied migration in `drizzle.__drizzle_migrations` — schema `drizzle`, columns
`id`, `hash`, `created_at`.

Render applies them automatically: `apps/api/render.yaml` sets

```yaml
preDeployCommand: cd packages/db && bun run db:migrate
```

which Render runs once per deploy, after the build and before traffic cuts over
to the new instance, in the service's own environment.

**Drizzle decides what to apply by `created_at`, not by hash-matching each file.**
It takes the newest `created_at` in the journal and applies every migration whose
folder timestamp is newer. An empty journal therefore means "apply everything",
regardless of what actually exists in the database.

## The rule

**Apply migrations only through `db:migrate`.** Never paste migration SQL into the
Supabase SQL Editor, psql, or any other client, even to "just get it applied" —
see below for exactly what that costs.

## Known hazards

### Applying migrations by hand desyncs the journal, and the next deploy fails

Pasting the migration SQL into the Supabase SQL Editor creates the tables and
types but writes nothing to `drizzle.__drizzle_migrations`. The next `db:migrate`
sees an empty journal, replays `0000_initial`, and exits 1 on the first object
that already exists:

```
PostgresError: type "actor_type" already exists
```

Because that command is Render's `preDeployCommand`, the failure **fails the
entire deploy**. The dangerous part is how quiet it is: the API keeps serving the
last image that deployed successfully, so commits look merged and shipped while
production runs older code. This has already cost real debugging time once —
several auth fixes were investigated in production before anyone noticed they had
never actually deployed.

**Recovery:** run `packages/db/scripts/baseline-journal.sql` against the affected
database (the same `DATABASE_URL` Render uses), then redeploy. It records
migrations 0000-0005 as applied using Drizzle's own hashes, is idempotent, and
touches no application data or schema. It does not verify that the schema truly
matches those migrations — only use it when the schema really was created from
those exact files.

**Diagnosing:** `SELECT count(*) FROM drizzle.__drizzle_migrations;` — if the
tables exist but this is 0 (or lower than the migration count), the journal has
desynced.

### A migration failure takes the whole API down with it

`preDeployCommand` couples deployability to migration success: any failing
migration blocks the deploy entirely, including deploys that contain no schema
change at all. That is a deliberate trade (never serve code against an
un-migrated database) but it means a bad migration is an outage of the deploy
pipeline, not just of one feature.

**Gap:** there is no migration rollback path. `drizzle-kit` generates forward-only
SQL, and no down-migrations are written. Recovering a bad migration today means
writing a corrective forward migration, or restoring from Supabase PITR.

### Seeding is deliberately not automated

`db:seed` is **not** in `preDeployCommand` — it is a one-time/manual step, and
re-running it on every deploy would write fixture rows over real user data. Run
`bun run db:seed` by hand against the target `DATABASE_URL` after the first
successful migration if reference data (partners, instruments, planning products)
is not loaded yet.

## Checking what production actually has

```sql
-- how many migrations does the journal think are applied?
SELECT id, hash, created_at FROM drizzle.__drizzle_migrations ORDER BY id;

-- does the schema exist at all?
SELECT count(*) FROM information_schema.tables WHERE table_schema = 'public';
```

If the second is non-zero and the first is empty, that is the desync above.
